# 引擎集成评估报告

> 最后更新: 2026-07-24
>
> 数据来源：18 个竞品仓库分析，按优先级分类

## P1 评估项（短期 1-4 周）

### GPT-SoVITS（5 秒零样本克隆 + 1 分钟微调）

| 维度 | 评估 |
|------|------|
| 许可证 | MIT — 可直接商用 |
| 核心能力 | 5 秒零样本克隆、1 分钟微调、中日英韩粤 G2P |
| 架构 | GPT + SoVITS 双阶段、CFM v3 声码器 |
| 显存需求 | ~4GB（推理）、~8GB（训练） |
| 依赖冲突 | gradio<5 + peft<0.18.0 + torchmetrics<=1.5 约束严格 |
| 集成方案 | 作为 `engines/gpt_sovits/` 独立模块，需虚拟环境隔离依赖 |
| 风险 | 依赖版本约束与 VoxCPM2 可能冲突，需 venv 隔离 |

**结论**：建议集成，补充少样本训练短板。优先实现推理接口，训练功能后续迭代。

### AutoModel 工厂模式（参考 CosyVoice）

| 维度 | 评估 |
|------|------|
| 设计思路 | `AutoModel.from_pretrained(config)` 配置驱动实例化 |
| 当前状态 | 已实现 InMemoryEngineRegistry + 懒导入机制 |
| 差距 | 缺少 from_pretrained 统一入口、配置驱动参数选择 |
| 实施方案 | 在 EngineRegistry 基础上增加 `create_engine(name, config)` 工厂方法 |

**结论**：当前 InMemoryEngineRegistry 已覆盖核心需求，AutoModel 工厂作为 P1 后续优化。

## P2 评估项（中期 1-3 月）

### CosyVoice v3（LLM + Flow Matching）

| 维度 | 评估 |
|------|------|
| 许可证 | Apache 2.0（代码），ModelScope 条款（模型） |
| 核心能力 | Instruct 指令控制语言/方言/情感/语速 |
| 显存需求 | ~8GB（推理） |
| 集成价值 | 高 — 指令式控制能力与现有引擎互补 |
| 依赖 | funasr + matcha-tts + vocos，与 VoxCPM2 有 funasr 共用 |

**结论**：中期评估集成，Instruct 控制能力可增强用户体验。

### ChatTTS（双阶段 GPT + GFSQ）

| 维度 | 评估 |
|------|------|
| 许可证 | **AGPLv3+ / CC BY-NC 4.0** — 非商用许可 ⚠️ |
| 核心能力 | 对话式场景突出、韵律控制标签 [laugh]/[uv_break] |
| 显存需求 | ~4GB |
| 法律风险 | **AGPL 传染性 + CC BY-NC 非商用限制** |

**结论**：⚠️ **不建议商用集成**。仅可用于内部评估和参考设计。韵律标签设计可借鉴。

### Edge-TTS（云端降级引擎）

| 维度 | 评估 |
|------|------|
| 许可证 | LGPLv3 — 需动态链接 |
| 核心能力 | 零 GPU 占用、70+ 语言、WebSocket 流式 |
| 显存需求 | 0 GB（调用微软 API） |
| 集成价值 | 高 — 无 GPU 环境降级方案 |
| 网络 | 需要互联网连接 |
| 限制 | 音色固定、无法克隆、有调用频率限制 |

**结论**：建议作为 CPU 兜底引擎集成，需注意 LGPLv3 动态链接要求。

### Piper（轻量级边缘引擎）

| 维度 | 评估 |
|------|------|
| 许可证 | Apache 2.0 — 可商用 |
| 核心能力 | C++ 推理 + ONNX、CPU 实时、多质量分级 |
| 显存需求 | < 1 GB |
| 集成价值 | 中 — 边缘设备部署方案 |

**结论**：适合低配设备场景，中期评估。

### EmotiVoice（PromptTTS 情感控制）

| 维度 | 评估 |
|------|------|
| 许可证 | MIT — 可商用 |

|------|------|

**结论**：P3 长期评估，技术先进但集成复杂。

## 依赖隔离方案

由于多引擎依赖冲突风险（PyTorch/transformers/numpy 版本不兼容），推荐方案：

1. **进程级隔离**：每个引擎独立子进程，通过 gRPC/ZeroMQ 通信
2. **虚拟环境隔离**：每个引擎使用独立 venv，主进程通过 subprocess 调用
3. **Docker 容器隔离**：每个引擎独立容器，通过 REST API 通信

推荐优先实施进程级隔离（方案 1），兼顾性能和隔离性。
